Here's what I was able to determine from inspecting your live site, and a prioritised action list. The site appears to be a single-page app (looks like Ionic/Angular based on the plt-tablet plt-mobile md HTML classes), bundled into one big JS file: index-Cy7pkWkh.js. That single bundle plus several third-party widgets is the main reason mobile is at 56.
The actual culprits I identified on your live site
The biggest performance drag is third-party scripts loading on initial page load. You have eight external scripts firing, including Google Tag Manager / GA4 (gtag/js?id=G-Z5TMS725JR), Leadsy AI tracking (r2.leadsy.ai/tag.js), the LeadConnector chat widget (three separate files: chat-widget.esm.js, chat-widget.js, and loader.js), and libphonenumber-min.js from LeadConnector. The chat widget alone pulls in multiple sub-bundles (p-Do7bswAW.js, p-CQvax5BZ.js, p-r-p9EKsg.js) and a full iframe. This is your single biggest mobile performance killer — the chat widget is doing a lot of work before the user has even interacted.
Your fonts setup is also inefficient. You're loading Roboto from fonts.bunny.net four separate times with different query strings (regular, bold, and two with full fallback stacks in the URL), but you're also preconnecting to fonts.googleapis.com and fonts.gstatic.com which you don't appear to actually use. That's wasted DNS/TLS work plus duplicated font CSS requests.
Your main app bundle index-Cy7pkWkh.js is loaded synchronously (no async/defer), so it's render-blocking. Combined with the CSS bundle index-B8UIeiZj.css also being render-blocking, this directly hurts FCP and LCP.
PageSpeed reported ~365 KiB of unused JavaScript and ~16 KiB of unused CSS — typical of a bundled SPA where the homepage doesn't need everything. There are also six long main-thread tasks and a forced reflow being detected.
Prioritised fix list (highest impact first)

Defer the chat widget until user interaction. Instead of loading widgets.leadconnectorhq.com/loader.js in the initial HTML, load it on first scroll, after a 3–5 second delay, or when the user clicks a "chat" button. This single change will likely jump mobile performance from 56 to 75+. Same approach for r2.leadsy.ai/tag.js.
Defer or delay GA4. Load gtag/js after the page is interactive, or via Partytown to move it off the main thread. Alternatively, use GA4 measurement protocol server-side.
Consolidate the font requests. Replace the four separate fonts.bunny.net/css?family=Roboto... requests with a single request: https://fonts.bunny.net/css?family=roboto:400,700&display=swap. Add font-display: swap and remove the unused fonts.googleapis.com / fonts.gstatic.com preconnects.
Add defer to your main bundle. Change <script src="/assets/index-Cy7pkWkh.js"> to <script src="/assets/index-Cy7pkWkh.js" defer> so it doesn't block rendering.
Code-split the bundle. If this is built with Vite (the hash format suggests it), enable route-based code splitting so the homepage only ships what it needs. This addresses the 365 KiB unused JS.
Set long cache lifetimes on /assets/*. Configure your host (Cloudflare, Netlify, Vercel, or whatever you're on) to set Cache-Control: public, max-age=31536000, immutable on hashed asset files. Lighthouse flagged this as ~82 KiB of repeat-visit savings.
Preload the LCP element. Whatever the largest hero image or text element is, add a <link rel="preload"> for its critical resource.
Accessibility (90 → 100): Lighthouse flagged that some form elements don't have associated labels. Add <label for="..."> or aria-label to every input/select on the page (likely the chat widget contact form fields).

Realistic outcome of these changes
Implementing items 1–4 alone should get mobile from 56 into the 80s and desktop from 82 to 95+. Items 5–8 push toward the high 90s. Hitting a literal 100 on mobile while keeping GA4 and a chat widget on the page is unlikely — those tools inherently cost performance budget, and the trade-off is usually not worth it for a 1-point gain.
