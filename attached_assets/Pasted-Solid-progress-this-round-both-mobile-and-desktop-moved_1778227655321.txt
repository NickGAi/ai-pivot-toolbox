What's still holding the scores back
The bottleneck now is no longer the bundle structure — it's network-level. On mobile, FCP is still 6.0 s and LCP 7.8 s. With TBT only 70 ms, the main thread isn't the problem anymore. The page is just waiting on the network to deliver the initial HTML, CSS, and Hero/Navbar JS chunk over Slow 4G.

Suggested next moves
The biggest remaining opportunity is the LCP/FCP on mobile, which is now network-bound. The fix is inlining critical CSS for the Hero/Navbar above-the-fold render and async-loading the rest of the stylesheet. In Vite this is typically done with a critical CSS plugin or by manually splitting the CSS so the hero's styles ship inline in index.html and the rest loads via a preload/onload pattern.
Second: audit what's in the Hero chunk. If Framer Motion is only animating the hero's entrance, consider replacing that one animation with a CSS keyframe so the entire Framer Motion library can move into the lazy below-the-fold chunk. That alone could shave 50–100 KiB off the initial bundle.
Third: check the new Best Practices warning on desktop — open Chrome DevTools console on the live site and see what's being logged or flagged.
Realistically, mobile 60 → 90+ from here requires either a CDN/edge layer to reduce TTFB and asset latency, or going further with critical CSS inlining and image preloading for the hero. The pure JS bundle work is mostly done — diminishing returns from here on the bundle side.
